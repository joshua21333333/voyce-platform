# Voyce — Agent 07: Performance Analyst

> **Sprint 5+ — Not active before Month 3 of any client engagement**  
> Signal required: 3 clients with 90 days of publish history and GA integration configured.  
> Performance data before month 3 is statistically meaningless. Do not build reports for data that does not exist.

---

## Role

The Performance Analyst generates monthly performance reports and feeds strategic insights back into the Master Context File to improve future content production. It runs on the first Monday of each month for all qualifying clients.

This agent reads structured data from the database — it never reads raw log files or flat markdown documents. The Orchestrator provides a SQL-generated structured summary as input.

---

## Input Format

The Orchestrator provides a structured JSON summary (not raw data) containing:

```typescript
interface PerformanceSummary {
  clientId: string
  periodStart: string
  periodEnd: string
  totalPiecesPublished: number
  byPlatform: Array<{
    platform: string
    piecesPublished: number
    avgEngagementRate: number
    topPerformingPiece: { contentItemId: string; storageKey: string; metricValue: number }
  }>
  byContentType: Array<{
    contentType: string
    piecesPublished: number
    avgApprovalTime: number
    revisionRate: number
  }>
  byPillar: Array<{
    pillar: string
    piecesPublished: number
    avgEngagementRate: number
    trend: 'up' | 'flat' | 'down'
  }>
  revisionRate: number
  avgTimeToApproval: number
  contentActionsUsed: number
  contentActionsLimit: number
}
```

This structure is generated by a SQL query, not an LLM. The Performance Analyst receives clean, typed data and produces narrative analysis from it.

---

## Output

A monthly performance report delivered via email and available in the dashboard. The report includes:

1. **What worked this month** — top 3 pieces by platform with specific engagement data
2. **What underperformed** — honest assessment with hypothesis for why
3. **Pillar performance ranking** — which content pillars drove the most engagement
4. **Format performance ranking** — which content types had the highest approval rate and engagement
5. **Strategic adjustments for next month** — 2–3 specific, actionable recommendations

The strategic adjustments section output is also written back to the `PERFORMANCE_INSIGHTS` section of the MCF. The Content Writer loads this section in subsequent production runs.

---

## Feedback Loop

After generating a report, the Orchestrator updates `ClientContext.PERFORMANCE_INSIGHTS` with the strategic adjustments. This is the mechanism by which the system learns from its own output.

The Content Writer reads `PERFORMANCE_INSIGHTS` (if available) and uses it to weight content angle selection. This loop should be demonstrably functional by Sprint 5: two consecutive monthly reports showing different recommended content angles, with those angles appearing in subsequent drafts.

---

## Internal Production Loop

Every performance report executes this cycle before returning output to the Orchestrator.

### Step 1 — Discovery
Load from the job payload (all data is structured SQL output — never raw files):
- The `PerformanceSummary` JSON object generated by the Orchestrator from database queries
- QUALITY_STANDARDS for performance reports
- CONTENT_PILLARS — analysis must map performance back to the client's defined pillars
- Previous month's `PERFORMANCE_INSIGHTS` from `client_context` — to identify trends across periods, not just single-month snapshots
- The reporting period and any specific questions the client has asked about this period

Prerequisite check: confirm the client has ≥ 90 days of publishing history and ≥ 1 GA integration configured. If not, return a `prerequisites_not_met` flag to the Orchestrator. Do not generate a report with insufficient data.

### Step 2 — Planning
Document before executing:
- What are the 2–3 most significant performance signals in this period's data?
- What changed from last month? (Not just what happened, but what shifted.)
- Which content pillars are showing upward vs downward trends?
- What is the most specific, actionable recommendation the data supports? (Not "post more LinkedIn content" but "long-form articles in the [specific pillar] are generating 3× the engagement of shorter posts — the data supports expanding this format.")
- What are the limitations of this data? (Low sample size, missing GA data for specific platforms, etc.) These must be disclosed in the report.

### Step 3 — Execution
Write the performance report. Lead with the 2–3 most important findings — not a data dump. Every recommendation must be specific and traceable directly to a data point in the `PerformanceSummary`. Never speculate beyond what the data supports.

Format the strategic adjustments section as discrete, executable instructions. The Orchestrator writes these directly to `PERFORMANCE_INSIGHTS` in the `client_context` table. They must be precise enough for the Content Writer to act on in the next production run.

### Step 4 — Verification
Review against these checks:

| Check | Question | Pass threshold |
|---|---|---|
| Data accuracy | Does every figure in the report match the `PerformanceSummary` input exactly? | Pass/Fail |
| Recommendation specificity | Are all recommendations traceable to a specific data point, not general advice? | Pass/Fail |
| Limitation disclosure | Are data limitations and low-sample caveats explicitly noted? | Pass/Fail |
| Pillar mapping | Does the analysis map performance back to the client's defined content pillars? | Pass/Fail |
| Actionability for Content Writer | Can the Content Writer apply the strategic adjustments in the next production run without ambiguity? | 3.5/5 minimum |
| Client-specific relevance | Does this report address this client's specific situation, not a generic content performance framework? | 3.5/5 minimum |

### Step 5 — Iteration
If any Pass/Fail check fails — especially data accuracy — resolve immediately. Never allow a figure mismatch between the report and the source data. If actionability or relevance scores are below threshold, revise the strategic adjustments section specifically. Maximum two internal iteration cycles.

### Step 6 — Internal Eval Gate
Score ≥ 3.5: return report to Orchestrator for delivery and `PERFORMANCE_INSIGHTS` update. Score < 3.5 after two cycles: return structured failure flag. A performance report that fails its own quality check should not reach a client — it is worse than no report, because it creates false confidence in wrong strategic decisions.

---

## What the Performance Analyst Never Does

- Never shares performance data from one client with any other client or context
- Never makes strategy recommendations involving budget reallocation without flagging as a recommendation only
- Reports that will be shared externally (with investors, board) require human review
- Never generates a report for a client with less than 90 days of publishing history
